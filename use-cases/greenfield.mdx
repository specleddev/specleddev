---
title: "Greenfield"
description: "Start a new project with one small subject and one working verification loop."
---

Use this when you are starting from zero and want clear intent from day one without turning the repo into a planning exercise.

## Goal

Get one working loop in place early:

- one current-truth subject
- one set of requirements
- one real verification path
- one CI check that keeps drift visible

## Smallest good starting point

Pick one user-visible behavior.

Good examples:

- one endpoint
- one workflow
- one core module contract

Keep the first subject small enough that one engineer can hold the whole thing in their head.

## Recommended loop

1. Add the `.spec` workspace for your stack.
2. Write one subject spec in `.spec/specs/`.
3. Keep the first spec narrow:
   - two or three requirements
   - one or two scenarios
   - one verification target
4. Implement the code, tests, and docs from that contract.
5. Run the local verification command and keep the same check in CI.

## What success looks like

By the end of the first pass, the repo should have:

- one clear subject spec
- tests or commands that prove the key requirements
- a local verification command that passes
- a CI check that will fail when code and intent drift apart

That is enough to establish the method.

## Avoid

- modeling the whole project on day one
- writing specs for things nobody understands yet
- adding a large governance layer before the first verification loop works
- treating the spec as a substitute for tests

## Next step

Once the first subject is stable, add the next subject right beside it.

That keeps the adoption curve shallow and the method teachable.

Passing output:

```text
$ npx specled verify

Spec Led Verify

Specs scanned: 3
Subjects: 1
Requirements: 2
Scenarios: 2
Verification targets: 1

OK    .spec/specs/greeting-endpoint.spec.md
OK    src/app.test.ts covers 2 requirements

Updated .spec/state.json

Result: 0 findings
```

`verify` updates `.spec/state.json` with the current spec index and findings.

That file gives the tool one place to track current spec state.

## Show drift on purpose

Now imagine the test no longer checks the missing-name case.

Run `verify` again:

```bash
npx specled verify
```

Example drift output:

```text
$ npx specled verify

Spec Led Verify

WARN  requirement greeting.name_missing has no matching verification
WARN  src/app.test.ts does not assert status 400

Updated .spec/state.json

Result: 2 findings
```

## Run `check`

`check` is the gate.

If there is drift:

```text
$ npx specled check

Spec Led Check

FAIL 2 findings
See .spec/state.json
```

If the repo is aligned:

```text
$ npx specled check

Spec Led Check

PASS 0 findings
```

It is the same loop, just enforced strictly.

## Add CI

Use the same command in CI.

```yaml
name: spec-check

on:
  pull_request:
  push:
    branches: [main]

jobs:
  spec-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npx specled check
```

## What to skip

Do not start with:

- heavy traceability
- proposal records
- ADR workflows
- conformance matrices
- pre-commit hooks

Those can come later.

---
title: "Agent Prompts"
description: "Copyable prompts for using Spec Led Development with coding agents."
---

Keep prompts narrow.

The fastest way to get good results is to give the agent one slice, one goal, and one verification loop.

## Prompt: draft a new subject spec

```text
Read the repo's current .spec workspace and draft one new subject spec for <module or workflow>.

Keep the subject narrow.
Write current truth, not aspiration.
Use clear requirement ids.
Add only the scenarios that clarify important behavior.
Tie the subject to the smallest real verification target you can find.

End by running the repo's spec verification command and fix any findings.
```

## Prompt: refine a coarse spec

```text
Read this subject spec and the code, tests, and docs it points at.

It is too broad.
Refine it into a smaller set of sharper requirements.
If the subject boundary is too wide, split it into smaller current-truth subjects.

Do not invent new behavior.
Stay grounded in current shipped behavior.
End by running the repo's spec verification loop.
```

## Prompt: retrofit a brownfield module

```text
Treat this as a brownfield retrofit.

Read the current implementation and tests for <module>.
Write the smallest current-truth subject spec that matches what the repo already does.
Do not try to model the whole area.
Choose one important slice and tie it to real evidence.

If the repo has ADRs, reference only the ones that truly affect this subject.
Run the spec checks at the end.
```

## Prompt: fix a bug with spec updates

```text
Fix this bug through the full Spec Led Development loop.

First update the current-truth spec so the intended behavior is explicit.
Then change the code and tests to match.
If the change is cross-cutting, add or update an ADR.

End by running the repo's verification commands and summarize:
1. what changed in the spec
2. what changed in the code
3. what proof now covers the fix
```

## Prompt: review a pull request against the spec

```text
Review this change through the Spec Led Development lens.

Check:
1. whether the current-truth spec changed when behavior changed
2. whether the code matches the updated current truth
3. whether tests, docs, and verification targets prove the intended effect
4. whether any cross-cutting change should add or update an ADR

Call out concrete gaps or drift risks with file references.
```

## Prompt: keep the agent focused on one phase

```text
Work only on phase 1 of this plan.

Do not jump ahead.
Treat the roadmap as planning context, not current truth.
Only update:
- the subject specs needed for phase 1
- the code and tests for phase 1
- any ADRs needed for phase 1

Ignore later phases unless they change the current truth of this phase.
```

## A few rules that help

- keep one prompt focused on one slice
- ask for current truth, not a product vision dump
- ask the agent to run the verification loop
- use roadmap docs as working context, not as a replacement for specs
- ask for file references in the summary

---
title: "Background Theory"
description: "The core thinking behind Spec Led Dev."
---

Spec Led Dev starts from one simple observation:

software changes faster than shared understanding.

That creates the same failures again and again:

- behavior drifts from intent
- tests pass but the contract is unclear
- docs lag behind code
- new team members take too long to understand what matters
- AI makes plausible changes without enough context

## The core problem

Code explains *how* a system works, but it does not always explain *what must stay true*.

Teams need a stable way to declare intent inside the repository itself.

## The core idea

Write small, explicit spec files next to the code.

Each spec describes:

- the subject being specified
- the requirements that must hold
- scenarios that show expected behavior
- verification targets that should prove the claim
- exceptions when a deviation is intentionally approved

This creates a shared contract for humans and AI.

## Why this works

Spec Led Dev keeps a clean split:

- authored specs declare ideal state
- tooling derives drift and findings
- exceptions are explicit approvals

This avoids mixing desired behavior with operational status.

## Humans and AI, same source of truth

Humans use specs to understand a codebase quickly in GitHub.

AI uses specs as bounded instructions when making changes.

That makes AI more useful for maintenance work:

- update code toward declared intent
- update tests and docs with the change
- reduce guesswork during remediation

## Language-agnostic by design

The model is based on conceptual subjects, not programming language syntax.

The same structure works for:

- packages
- modules
- APIs
- services
- workflows
- repository policies

## Practical outcome

Spec Led Dev does not try to generate an entire system from prose.

It gives teams a durable contract layer so software can evolve without losing meaning.

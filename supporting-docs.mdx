---
title: "Supporting Docs"
description: "Where roadmaps, ADRs, and other useful docs should live."
---

Not every useful document belongs in `.spec/specs/`.

That folder has a narrow job:
durable current truth.

Keeping that boundary clear makes the method easier to teach and easier to maintain.

## What belongs in `.spec/specs/`

Keep this folder for current-truth subject specs.

That means:

- subject boundaries
- requirements
- scenarios
- verification targets
- exceptions

These files should describe what the repository should keep true now.

## What belongs in `.spec/decisions/`

Use ADRs for durable cross-cutting decisions.

Good ADR topics:

- verification policy
- subject decomposition choices
- package-wide workflow rules
- cross-cutting architectural decisions

Do not use ADRs for every local implementation choice.

## Where roadmaps and phase docs should go

Roadmaps are useful.
Phase plans are useful.
Working notes are useful.

They should live in a clearly non-core place.

Good options:

- `docs/roadmap.md`
- `docs/phases.md`
- `.spec/notes/roadmap.md`
- `.spec/notes/<topic>.md`

What matters is the boundary:

- `.spec/specs/` is current truth
- `.spec/decisions/` is durable cross-cutting decisions
- roadmap and planning docs are supporting context

## Why this boundary matters

If planning docs mix with current-truth specs, two problems show up fast:

1. in-flight thinking gets mistaken for merged truth
2. agents start treating planning notes as the contract

That creates confusion in review and drift in implementation.

## A good working pattern

Use the documents together, but give each one a clear job:

1. roadmap or phase doc says what you are trying to tackle next
2. ADR says what cross-cutting decision should stay consistent
3. current-truth spec says what the repo should keep true now
4. code, tests, and docs implement that truth
5. verification proves the co-change

Git history and pull requests carry the time dimension.
The `.spec` core carries the durable contract.

## Quick rule

If a document describes current truth, it probably belongs in `.spec/specs/`.

If it describes a cross-cutting decision, it probably belongs in `.spec/decisions/`.

If it describes planning, phases, or working notes, keep it outside the core spec folder.

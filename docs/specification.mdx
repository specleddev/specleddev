---
title: "Specification"
description: "The authored format and core data model for Spec Led documents."
---

Spec Led uses a repo-native authored format:

- `*.spec.md`

Each file is meant to be readable by humans and structured enough for tooling.

## Core entities

### Subject

The thing being specified.

Examples:

- package
- module
- component
- service
- API
- workflow

### Requirement

A normative claim about what must be true.

Recommended style:

- `When <trigger>, the <subject> shall <response>.`
- `If <precondition>, then the <subject> shall <response>.`
- `While <state>, the <subject> shall <response>.`

### Scenario

A concrete example of behavior.

Recommended style:

- `Given ...`
- `When ...`
- `Then ...`

### Verification

Expected evidence for the claim.

Examples:

- a test file
- a guide
- a command
- a workflow file
- an API contract

### Exception

An approved deviation from the ideal.

Anything not represented as an exception should be treated as drift by tooling.

## Structured blocks

Each spec document contains one `spec-meta` block and may include:

- `spec-requirements`
- `spec-scenarios`
- `spec-verification`
- `spec-exceptions`

## Example

````md
# Jido.Instruction

Instructions normalize action inputs into a stable instruction envelope.

```spec-meta
{
  "id": "module.jido_instruction",
  "kind": "module",
  "status": "active",
  "surface": ["Jido.Instruction"]
}
```

## Requirements

```spec-requirements
[
  {
    "id": "instruction.normalize.input_forms",
    "statement": "When normalization is invoked with modules, tuples, or structs, the instruction normalizer shall return a normalized instruction envelope.",
    "priority": "must",
    "stability": "stable"
  }
]
```

## Verification

```spec-verification
[
  {
    "kind": "test_file",
    "target": "test/jido_action/instruction_test.exs",
    "covers": ["instruction.normalize.input_forms"]
  }
]
```
````

## Important boundary

The authored spec represents the ideal state.

Findings, missing coverage, drift summaries, and action history should be generated by tooling instead of being written into the source spec itself.
